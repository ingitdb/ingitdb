# Idea: Computed Columns & Scripted Materialized Views (language-agnostic)

**Owner:** alexander.trakhimenok@gmail.com
**Promotes To:** computed-columns, formula-reference-wasm-engine

## Problem Statement

How might we define computed columns (inline formulas) and scripted materialized views as a normative, language-agnostic part of the inGitDB standard, so every implementation — the Go CLI, a TypeScript client, and future ones — computes byte-identical results from the same schema and data?

## Context

The ingitdb-cli (Go) reference implementation has shipped computed columns: an inline formula on a column, evaluated in a sandboxed, deterministic Starlark expression engine, surfaced on read and enforced for write-time foreign keys. This standard repo defines the normative inGitDB format and already carries materialized-views and referential-integrity features, but says nothing about computed values or view-generation logic. Without a normative spec, each implementation (Go, TypeScript) would invent its own formula language and semantics, and the same schema would produce different results across clients — breaking the 'one database, many implementations' promise.

## Recommended Direction

Add two normative capabilities to the standard: (1) computed columns — a column may declare an inline expression whose value is derived from the record's stored fields; and (2) scripted materialized views — a view may be generated by a script over a collection's records, extending the existing materialized-views feature beyond declarative projection. The decisive constraint, different from a single-language implementation, is cross-runtime determinism: the chosen expression/script language MUST have a formal semantics and a shared conformance test suite so every implementation yields identical output. The standard therefore specifies behavior plus a set of input-to-output conformance vectors that any implementation must pass, rather than mandating a particular embedding library. The decisive enabler for cross-platform reach is as much a *distribution* choice as a language choice: compile a single sandboxed interpreter to WebAssembly and embed that *identical* engine in every host — Go via wazero, Node and the browser via wasm. Byte-identical results then follow from running the same engine everywhere, not from independent engines agreeing. This reframes the language decision and, notably, removes the only serious strike against Starlark — its thin native TypeScript support — because the engine is shipped as one WASM module rather than reimplemented per language.

On that footing the standard adopts **Starlark compiled to WASM** as its engine (`starlark-go` is pure Go and compiles to wasm; `starlark-rust`, the engine behind Buck2, compiles to a compact, fast wasm): it keeps the language the Go reference implementation already uses, has real integer types and deterministic-by-design semantics, and — shipped as one shared WASM module embedded in every host (Go via wazero, Node and the browser via wasm) — runs everywhere with byte-identical results by construction. The conformance vectors remain the normative contract, complementing rather than replacing the shared engine.

The candidates not chosen: **sandboxed JavaScript** (e.g. QuickJS-WASM) — a strong option had one *imperative*, universally-familiar language for both formulas and Phase-2 view scripts been the priority, but it has no native integer type and needs a restricted deterministic profile (no `Math` transcendentals, `Date`, `Intl`, locale, or randomness); and **CEL** — typed but expression-only, so unable to express imperative view scripts.

## Alternatives Considered

The live *language* candidates (Starlark-via-WASM, sandboxed JavaScript-via-WASM,
CEL) are weighed in the Recommended Direction. The directions below are the ones this
Idea sets aside.

**Multiple independently-conformant native engines (no shared WASM engine).** Each
implementation embeds its own native interpreter (starlark-go in Go, a Starlark-in-TS
or CEL-js in TypeScript, …) kept in agreement only by the conformance suite. Set aside
in favor of a single shared WASM engine, which makes agreement *structural* (the same
bytecode runs everywhere) rather than *tested after the fact*. It remains the fallback
if a WASM engine proves too heavy or slow for a particular host (e.g. very constrained
browser budgets), in which case the conformance vectors become the only guarantee.

**Per-implementation language (no normative engine).** Let each implementation pick
its own expression language and only standardize the column attribute. Rejected
outright: it guarantees the same schema produces different values across clients,
which defeats the entire "one database, many implementations" premise.

**Declarative-only computed values (no expression language).** Extend the existing
declarative transforms (format strings, field references, a simple arithmetic DSL)
instead of a real expression language. Lost because it cannot express the
conditionals, string operations, and arithmetic real formulas need, and a growing
config DSL ends up reinventing an expression language with no formal semantics — the
worst position for a cross-language standard.

## MVP Scope

A normative computed-column specification for inline expressions over stored scalar fields — supported types, evaluation timing (compute-on-read), type coercion, deterministic sandbox (no I/O/clock/random) — accompanied by a language-agnostic conformance test suite (input record + formula + expected output vectors) that the Go CLI and a second implementation (TypeScript) both pass. Scripted materialized views are scoped out of the MVP.

## Not Doing (and Why)

- Mandating a specific embedding library or runtime — the conformance vectors are the contract, not the implementation
- The full imperative scripted-view specification — deferred to Phase 2, extending the existing materialized-views feature
- Cross-collection reads or joins inside a computed-column formula — kept out to preserve per-record determinism
- Re-deciding the Go CLI's engine unilaterally — the standard defines the contract; the reference implementation reconciles to it

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | A single sandboxed interpreter (Starlark or QuickJS) can be compiled to WASM and embedded in both a Go host (wazero) and a TypeScript/browser host with identical behavior and no I/O | Spike: compile `starlark-go`→wasm and/or `starlark-rust`→wasm; run the same formulas in wazero and in the browser; diff outputs |
| Must-be-true | The numeric and string semantics (int vs float, division, rounding, unicode) can be pinned tightly enough that all implementations agree byte-for-byte — especially JavaScript, which has no native integer type | Author conformance vectors covering arithmetic, division, rounding, and string ops; run them against every host of the chosen engine |
| Should-be-true | The WASM engine's size and startup/per-eval cost are acceptable on each platform, including the browser | Measure wasm binary size and eval latency for `starlark-go`-wasm, `starlark-rust`-wasm, and QuickJS-wasm |
| Should-be-true | The Go reference implementation can reconcile to the standardized engine without losing shipped capabilities (it already embeds `starlark-go`, so a WASM/shared path is incremental) | Map every shipped ingitdb-cli formula behavior onto the candidate engine; identify gaps |
| Might-be-true | The same engine extends cleanly to Phase-2 scripted materialized views (imperative, multi-record), not just per-record expressions | Sketch a scripted-view example in the candidate language; confirm it stays deterministic and sandboxable |


## SpecScore Integration

- **New Features this would create:** a normative `computed-columns` Feature (inline-formula expressions, MVP); a `formula-conformance` Feature (or section) defining the cross-language conformance vectors; later, a scripted-views capability
- **Existing Features affected:** `materialized-views` (extended in Phase 2 to allow script-generated views); `collection-schema` (a column gains an optional formula attribute); `referential-integrity` (a computed column may be a foreign key, validated against the derived value)
- **Dependencies:** the ingitdb-cli (Go) reference implementation of computed columns as the proving ground; the chosen expression language's own cross-language conformance tooling

## Open Questions

- **Engine build:** `starlark-go`→wasm vs `starlark-rust`→wasm — weighed on wasm binary size, eval performance, browser startup cost, and maintenance. (The language — Starlark — and distribution — a single shared WASM engine — are decided.)
- What is the normative numeric model — `int` vs `float`, division (`/` vs `//`), rounding, and overflow — so results are byte-identical? (Simpler than JavaScript would have been, since Starlark has real integer types, but division and overflow semantics still need pinning.)
- In what format are conformance vectors published and versioned, and where do they live (this repo vs a shared test-vectors repo) so every implementation's CI consumes them?
- How does the Go reference implementation migrate from its current native `starlark-go` embedding to the shared WASM engine, and on what timeline (it already speaks Starlark, so this is reconciliation, not a rewrite)?
- For Phase-2 scripted views: how does a Starlark view script receive a collection's records and emit view rows (the contract surface), while staying deterministic and sandboxed?
