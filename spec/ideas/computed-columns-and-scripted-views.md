# Idea: Computed Columns & Scripted Materialized Views (language-agnostic)

## Problem Statement

How might we define computed columns (inline formulas) and scripted materialized views as a normative, language-agnostic part of the inGitDB standard, so every implementation — the Go CLI, a TypeScript client, and future ones — computes byte-identical results from the same schema and data?

## Context

The ingitdb-cli (Go) reference implementation has shipped computed columns: an inline formula on a column, evaluated in a sandboxed, deterministic Starlark expression engine, surfaced on read and enforced for write-time foreign keys. This standard repo defines the normative inGitDB format and already carries materialized-views and referential-integrity features, but says nothing about computed values or view-generation logic. Without a normative spec, each implementation (Go, TypeScript) would invent its own formula language and semantics, and the same schema would produce different results across clients — breaking the 'one database, many implementations' promise.

## Recommended Direction

Add two normative capabilities to the standard: (1) computed columns — a column may declare an inline expression whose value is derived from the record's stored fields; and (2) scripted materialized views — a view may be generated by a script over a collection's records, extending the existing materialized-views feature beyond declarative projection. The decisive constraint, different from a single-language implementation, is cross-runtime determinism: the chosen expression/script language MUST have a formal semantics and a shared conformance test suite so every implementation yields identical output. The standard therefore specifies behavior plus a set of input-to-output conformance vectors that any implementation must pass, rather than mandating a particular embedding library. The Go reference impl proves feasibility with Starlark; the open reconciliation is whether the standard adopts Starlark (multiple language impls, formal spec, but thin TypeScript support) or an expression language with first-class multi-language conformance such as CEL (cel-go + cel-js + an official conformance suite). The recommendation is to lead with a language that already has a published cross-language conformance suite, and to treat the conformance vectors — not the library — as the normative contract.

## Alternatives Considered

**Standardize on Starlark everywhere.** Adopt the Go reference impl's choice as
the normative language; every implementation must embed a conformant Starlark. Lost
(for now) because Starlark's cross-language story is uneven — mature in Go, Java, and
Rust, but there is no first-class, widely-used Starlark for TypeScript, so a JS/TS
client would carry a heavy or immature dependency. It remains a live candidate if the
TypeScript gap can be closed, since Starlark has a formal spec and is already proven
in the reference implementation.

**Per-implementation language (no normative engine).** Let each implementation pick
its own expression language and only standardize the column attribute. Rejected
outright: it guarantees the same schema produces different values across clients,
which defeats the entire "one database, many implementations" premise. The whole
point of putting this in the standard is byte-identical results.

**Declarative-only computed values (no expression language).** Extend the existing
declarative transforms (e.g. format strings, field references, simple arithmetic
DSL) instead of a real expression language. Lost because it cannot express the
conditionals, string operations, and arithmetic real formulas need, and a growing
config DSL ends up reinventing an expression language with no formal semantics —
the worst position for a cross-language standard.

**Expression language with a published cross-language conformance suite (e.g. CEL).**
CEL has cel-go, cel-js, and an official conformance test suite designed precisely for
multi-runtime agreement. This is the leading candidate *for the standard* even though
the Go reference impl shipped with Starlark — because the standard's hard constraint
is cross-language determinism, which a conformance suite directly serves. The cost is
reconciling the Go reference implementation (which would adopt CEL alongside or in
place of Starlark for standardized formulas).

## MVP Scope

A normative computed-column specification for inline expressions over stored scalar fields — supported types, evaluation timing (compute-on-read), type coercion, deterministic sandbox (no I/O/clock/random) — accompanied by a language-agnostic conformance test suite (input record + formula + expected output vectors) that the Go CLI and a second implementation (TypeScript) both pass. Scripted materialized views are scoped out of the MVP.

## Not Doing (and Why)

- Mandating a specific embedding library or runtime — the conformance vectors are the contract, not the implementation
- The full imperative scripted-view specification — deferred to Phase 2, extending the existing materialized-views feature
- Cross-collection reads or joins inside a computed-column formula — kept out to preserve per-record determinism
- Re-deciding the Go CLI's engine unilaterally — the standard defines the contract; the reference implementation reconciles to it

## Key Assumptions to Validate

| Tier | Assumption | How to validate |
|------|------------|-----------------|
| Must-be-true | A sandboxed, deterministic expression language exists with mature implementations in BOTH Go and TypeScript (the two implementations that exist today) | Build a tiny spike: evaluate a fixed set of formulas in cel-go and cel-js (and the Starlark equivalents) and diff the outputs |
| Must-be-true | The numeric and string semantics (int vs float, division, rounding, unicode) can be pinned tightly enough that all implementations agree byte-for-byte | Author cross-language conformance vectors covering arithmetic, division, rounding, and string ops; run them against every implementation |
| Should-be-true | The conformance-vector approach (data fixtures as the normative contract) is workable to author, version, and run in each implementation's CI | Prototype a vector format (e.g. JSONL of schema+record+formula+expected) and a runner in the Go CLI and a TS harness |
| Should-be-true | The Go reference implementation can reconcile to the standardized language without losing the capabilities already shipped | Map every shipped ingitdb-cli formula behavior to the candidate standard language; identify gaps |
| Might-be-true | The same engine and conformance approach extend cleanly to Phase-2 scripted materialized views (imperative, multi-record), not just per-record expressions | Sketch a scripted-view example in the candidate language; confirm it stays deterministic and sandboxable |


## SpecScore Integration

- **New Features this would create:** a normative `computed-columns` Feature (inline-formula expressions, MVP); a `formula-conformance` Feature (or section) defining the cross-language conformance vectors; later, a scripted-views capability
- **Existing Features affected:** `materialized-views` (extended in Phase 2 to allow script-generated views); `collection-schema` (a column gains an optional formula attribute); `referential-integrity` (a computed column may be a foreign key, validated against the derived value)
- **Dependencies:** the ingitdb-cli (Go) reference implementation of computed columns as the proving ground; the chosen expression language's own cross-language conformance tooling

## Open Questions

- Which expression language does the standard adopt — Starlark (proven in the Go reference impl, formal spec, thin TypeScript support) or CEL (cel-go + cel-js + official conformance suite)? This is the central decision and gates everything else.
- What is the normative numeric model across languages — integer vs float distinction, division (`/` vs `//`), rounding, and overflow — so results are byte-identical?
- In what format are conformance vectors published and versioned, and where do they live (this repo vs a shared test-vectors repo) so every implementation's CI can consume them?
- Does the Go reference implementation switch engines, run both, or stay on Starlark with a conformance shim — and on what timeline?
- For Phase-2 scripted views: does the same expression language suffice for imperative, multi-record view generation, or does that need a separate (still deterministic, still sandboxed) scripting capability?
